Code propre ​

Le code propre (clean code) se lit naturellement, révèle son intention et minimise le besoin de commentaires

La métrique informelle

Combien de « WTF / minute » génère-t-il à la lecture?

Même du code propre n'est pas exempt de WTF, il y en simplement moins / minute!

Objectifs d'apprentissage ​

Après cette section, tu seras capable de...

  • Identifier les caractéristiques d'un code propre
  • Appliquer les principes DRY et KISS
  • Restructurer une méthode avec des clauses de garde (early return / early failure)
  • Éliminer le code mort et les avertissements du compilateur
  • Nommer les classes, méthodes et variables de façon révélatrice

Les critères d'un code propre ​

Standards de format ​

  • Respect de la casse (PascalCase, camelCase, UPPER_SNAKE_CASE)
  • Indentation cohérente (4 espaces en Java)
    • À chaque nouveau niveau d'imbrication, on indente d'un niveau
  • Ordre de déclaration des membres : constantes → attributs → constructeurs → méthodes publiques → méthodes privées

Auto-formatage dans IntelliJ

Le formatage est pris en charge par IntelliJ, le raccourci clavier ctrl+alt+l permet de reformatter automatiquement votre code et de faire le nettoyage des importations non-requises.

Nommage révélateur ​

java
// ✗ Nommage opaque
int d;
void proc(List<int[]> l) { }

// ✓ Nommage révélateur
int joursDepuisCreation;
void filtrerArticlesExpires(List<Article> articles) { }

Constantes nommées - pas de valeurs magiques ​

java
// ✗
if (temperature > 37.5) { ... }

// ✓
if (temperature > SEUIL_FIEVRE) { ... }

Code nettoyé ​

  • Aucun avertissement (warning) du compilateur
  • Aucun import inutile
  • Aucun code mort (code commenté, méthodes jamais appelées)
  • Aucune variable déclarée mais jamais utilisée

Code non testé = Code mort

Du code qui n'est pas couvert par des tests (même s'il est utilisé par le code de production) est considéré comme du code mort dans le cadre du cours de PO2! Il doit donc être testé ou supprimé, mais ne peut pas être conservé tel quel!

Principes DRY et KISS ​

DRY - Don't Repeat Yourself ​

Toute connaissance doit avoir une représentation unique dans le système. La duplication de la connaissance est une dette technique qui se manifeste lors de chaque modification.

java
// ✗ Duplication - si le calcul change, il faut le modifier à 2 endroits
double totalHT = quantite * prixUnitaire;
double taxe = quantite * prixUnitaire * 0.15;

// ✓ DRY - une seule source de vérité
double totalHT = calculerTotalHT(quantite, prixUnitaire);
double taxe = totalHT * TAUX_TAXE;
Exemple complet DRY - Achat/Expédition[^1]

Voici 2 classes d'une boutique enligne pour l'achat et l'expédition de produits

PanierAchat

java
public class PanierAchat {
    public static final int NB_PRODUIT_MAX_AUTORISE = 3;
    private List<Produit> produits = new ArrayList<>();

    public void ajouterProduit(Produit produit) {
        if (produits.size() > NB_PRODUIT_MAX_AUTORISE) {
            throw new IllegalStateException(String.format(
                    "Nombre maximal (%d) d'exemplaires dépassé",
                    NB_PRODUIT_MAX_AUTORISE
            ));
        }
        produits.add(produit);
    }
}

ExpeditionService

java
public class ExpeditionService {
    public static final int NB_PRODUIT_MAX_AUTORISE = 3;
    private List<Produit> produits = new ArrayList<>();

    public void ajouterProduit(Produit produit) {
        if (produits.size() > NB_PRODUIT_MAX_AUTORISE) {
            throw new IllegalStateException(String.format(
                    "Nombre maximal (%d) d'exemplaires dépassé",
                    NB_PRODUIT_MAX_AUTORISE
            ));
        }
        produits.add(produit);
    }
}

En apparence, on brise le DRY ici, les 2 classes ont exactement le même code (constantes, attributs et méthodes), mais est-ce le cas?

Il faut se poser les questions suivantes:

  • Que représente PanierAchat.NB_PRODUIT_MAX_AUTORISE?
  • Que représente ExpeditionService.NB_PRODUIT_MAX_AUTORISE?

Les deux constantes contiennent la même valeur, mais est-ce le même concept dans le domaine d'affaire?

La contrainte pour le panier d'achat peut représenter un rareté des différents produits (ex: Playstation5 lors de la sortie) et on veut laisser la chance à chaque client la possibilité de se procurer les articles offerts

La contrainte pour le service d'expédition peut représenter une contrainte de l'expéditeur pour différents articles « dangereux » (ex: les bouteilles de propane d'un livre, très utile en camping) et on doit se conformer aux lois fédérales pour le transport de matières dangereuses.

Puisque les deux constantes représentent 2 connaissances différentes, la duplication est acceptable ici. De vouloir généraliser ce code serait une optimisation prématurée

[^1] Exemple adapté de https://verraes.net/2014/08/dry-is-about-knowledge/

KISS - Keep It Simple, Stupid ​

Le code le plus simple qui fonctionne est le bon code. La complexité accidentelle est l'ennemi de la maintenabilité.

java
// ✗ Complexité inutile
public boolean estAdulte(int age) {
    if (age >= 18) {
        return true;
    } else {
        return false;
    }
}

// ✓ KISS
boolean estAdulte(int age) {
    return age >= 18;
}

Clauses de garde - early return et early failure ​

Une clause de garde est une condition placée en tête de méthode qui rejette immédiatement les cas invalides ou hors-champ, avant d'exécuter la logique principale. Elle évite l'imbrication de conditions et rend le chemin normal (happy path) visible sans indentation.

Problème - imbrication en escalier ​

java
// ✗ Chaque condition ajoute un niveau d'indentation
public String formaterNom(String prenom, String nom) {
    if (prenom!= null) {
        if (!prenom.isBlank()) {
            if (nom!= null) {
                if (!nom.isBlank()) {
                    return prenom + " " + nom;
                }
            }
        }
    }
    return "";
}

Solution - clauses de garde avec early return ​

java
// ✓ Les cas invalides sont rejetés immédiatement
public String formaterNom(String prenom, String nom) {
    if (prenom == null || prenom.isBlank()) {
        return "";
    }
    if (nom == null || nom.isBlank()) {
        return "";
    }

    return prenom + " " + nom;  // chemin normal - toujours au même niveau
}

Chaque clause de garde inverse la condition originale et sort tôt. La logique principale reste au niveau zéro d'indentation.

Early failure - lancer une exception ​

Quand une valeur invalide représente une erreur de programmation plutôt qu'un cas normal, on lance une exception au lieu de retourner une valeur de repli.

java
// ✗ Logique principale enfouie dans le else
public double calculerTauxHoraire(double salaire, int heures) {
    if (salaire > 0) {
        if (heures > 0) {
            return salaire / heures;
        } else {
            throw new IllegalArgumentException("Les heures doivent être positives : " + heures);
        }
    } else {
        throw new IllegalArgumentException("Le salaire doit être positif : " + salaire);
    }
}

// ✓ Clauses de garde - les préconditions sont vérifiées d'abord
public double calculerTauxHoraire(double salaire, int heures) {
    if (salaire <= 0) {
        throw new IllegalArgumentException("Le salaire doit être positif : " + salaire);
    }
    if (heures <= 0) {
        throw new IllegalArgumentException("Les heures doivent être positives : " + heures);
    }

    return salaire / heures;
}

Lire les clauses de garde comme un contrat

Les clauses de garde en tête de méthode documentent les préconditions : « cette méthode suppose que X est valide - sinon, elle échoue immédiatement ». C'est une application du principe fail fast : mieux vaut planter tôt avec un message clair que d'obtenir un résultat silencieusement incorrect plus loin.

Exemple complet - méthode avec plusieurs gardes ​

java
void inscrireEtudiant(Etudiant etudiant, Cours cours) {
    if (etudiant == null) {
        throw new IllegalArgumentException("L'étudiant est requis.");
    }
    if (cours == null) {
        throw new IllegalArgumentException("Le cours est requis.");
    }
    if (!etudiant.aLesPrealables(cours)) {
        throw new IllegalStateException("L'Étudiant n'a pas complété les cours préalables requis")
    }
    if (cours.estComplet()) {
        throw new IllegalStateException("Le cours est complet, impossible de procéder à l'inscription")
    }

    cours.inscrire(etudiant);
    etudiant.ajouterCours(cours);
}

Les deux premiers if protègent contre des erreurs de programmation (arguments null). Les deux suivants traitent des cas d'affaire légitimes. La logique principale n'est atteinte que quand tout est valide.

Exemple de code propre - classe Employe
java
public class Employe {
    public static final double TAUX_AUGMENTATION_STANDARD = 0.03;

    private final String nom;
    private double salaire;

    public Employe(String nom, double salaire) {
        validerNom(nom);
        validerSalaire(salaire);
        this.nom = nom;
        this.salaire = salaire;
    }

    public void appliquerAugmentation(double taux) {
        validerTaux(taux);
        this.salaire *= (1 + taux);
    }

    public String getNom()     { return this.nom; }
    public double getSalaire() { return this.salaire; }

    private void validerNom(String nom) {
        if (nom == null || nom.isBlank()) {
            throw new IllegalArgumentException("Le nom ne peut pas être vide.");
        }
    }

    private void validerSalaire(double salaire) {
        if (salaire < 0) {
            throw new IllegalArgumentException("Le salaire ne peut pas être négatif.");
        }
    }

    private void validerTaux(double taux) {
        if (taux < 0 || taux > 1) {
            throw new IllegalArgumentException("Le taux doit être entre 0 et 1.");
        }
    }
}
