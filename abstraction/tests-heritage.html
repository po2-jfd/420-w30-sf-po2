Tester l'héritage ​

Une hiérarchie d'héritage se teste à deux endroits : dans la classe de tests de la super-classe, et dans la classe de tests de chaque sous-classe. Ce n'est pas de la redondance : les deux tests répondent à deux questions différentes.

Objectifs d'apprentissage ​

Après cette section, tu seras capable de...

  • Distinguer la vérification du LSP de la protection contre la régression
  • Tester les comportements hérités dans la classe de tests d'une sous-classe
  • Tester une classe abstraite via ses sous-classes concrètes
  • Choisir entre une sous-classe concrète existante, une classe de test privée et un mock

Deux raisons, un seul geste ​

Vérification du LSPProtection contre la régression
QuandÀ l'écriture de la sous-classePlus tard, quand la super-classe change
Échec du testÉchec immédiat du test, à l'écritureTest en succès qui devient en échec, sans raison apparente
DiagnosticLa sous-classeLa modification apportée à la super-classe

Règle ​

L'ensemble des comportements de la super-classe sont testés dans sa propre classe de tests et dans celle de chaque sous-classe. Un comportement hérité n'est pas exempté de test sous prétexte qu'il « vient d'ailleurs » - c'est justement ce lien qu'on veut vérifier.

Premier usage - vérifier le LSP ​

Le test qui tranche entre Rectangle et Carre est un exemple direct : on écrit ce test au moment même où on introduit Carre extends Rectangle, pas après coup.

java
// CarreTest

@Test
void etantDonneCarreUtiliseCommeRectangleLorsquOnModifieSaTailleAlorsSeComporteCommeUnRectangle() {
    Rectangle rectangle = new Carre(10);

    rectangle.setHauteur(5);

    assertEquals(50, rectangle.getAire()); // échoue dès l'écriture
}

Ce test échoue dès qu'on l'écrit. Le diagnostic porte sur Carre : la hiérarchie ne devrait probablement pas exister sous cette forme.

Tester les sous-classes

Lorsqu'on teste les comportements offerts par la super-classe, il faut traiter le test comme un test de la super-classe.

Le cas de test ci-dessus teste le Carre comme s'il était un Rectangle dans la classe CarreTest.

Second usage - protéger contre la régression ​

Livre.toString() et LivrePapier.toString() sont testés séparément :

java
public class Livre {
    private String auteur;
    private String titre;
    private String isbn;

    public Livre(String auteur, String titre, String isbn) {
        this.auteur = auteur;
        this.titre = titre;
        this.isbn = isbn;
    }

    public String getAuteur() { return this.auteur; }
    public String getTitre()  { return this.titre; }
    public String getIsbn()   { return this.isbn; }

    @Override
    public String toString() {
        return this.titre + " - " + this.auteur;
    }
}
java
// LivreTest
@Test
void etantDonneLivreLorsquOnAppelleToStringAlorsRetourneTitreEtAuteur() {
    Livre livre = new Livre("Robert C. Martin", "Clean Code", "978-0-13-235088-4");

    assertEquals("Clean Code - Robert C. Martin", livre.toString());
}
java
// LivrePapierTest
@Test
void etantDonneLivrePapierLorsquOnAppelleToStringAlorsRetourneTitreAuteurEtNombreDePages() {
    LivrePapier livre = new LivrePapier("Robert C. Martin", "Clean Code", "978-0-13-235088-4", 464);

    assertEquals("Clean Code - Robert C. Martin (464 pages)", livre.toString());
}

Un mois plus tard, le format de Livre.toString() change (le séparateur " - " devient ", par "). LivreTest est mis à jour en même temps que le changement - il reste en succès, puisque c'est le comportement voulu.

LivrePapierTest, lui, n'a pas été modifié directement : LivrePapier.toString() appelle toujours super.toString(). Par contre le format a changé et LivrePapierTest tombe en échec, la régression est détectée avant la mise en production.

Interpréter un échec de test ​

Carre/Rectangle ​

  • Signification de l'erreur : le test est en échec dès qu'on l'écrit, c'est impossible de rétablir le succès des tests de Carre sans changer la hiérarchie.
  • Identification du problème : Carre ne peut pas remplacer Rectangle, le LSP est enfreint.
  • Solution : remettre extends en question et revoir la hiérarchie. Réparer le code de Carre ne suffit pas, le test en erreur a déjà montré qu'aucun code ne peut régler l'erreur et faire passer le test.

Livre/LivrePapier ​

  • Signification de l'erreur : LivreTest et LivrePapierTest sont tous les deux en succès au départ. Après une modification à Livre.toString(), LivreTest reste en succès (mis à jour avec le changement voulu), mais LivrePapierTest tombe en échec sans qu'on y ait touché.
  • Identification du problème : régression : LivrePapier.toString() dépendait du format exact produit par super.toString(), et ce format a changé.
  • Solution : réparer LivrePapier pour qu'il tienne compte du nouveau format de Livre (ou ajuster Livre si le changement n'était pas voulu) - la hiérarchie elle-même n'est pas en cause.

Tester une classe abstraite ​

On ne peut jamais instancier une classe abstraite directement, elle se teste par ses sous-classes concrètes. Le contrat abstrait (les méthodes protected abstract, appelées depuis une méthode d'orchestration final) est testé dans chaque sous-classe, puisque chacune définit une implémentation différente.

java
@Test
void etantDonneEtudiantInformatiqueAvecUneMoyenneSousLeSeuilDeReussiteLorsquOnVerifieEstAdmisALaProchaineSessionAlorsNEstPasAdmis() {
    Etudiant etudiant = new EtudiantInformatique("Alice", List.of(50, 55));

    assertFalse(etudiant.estAdmisALaProchaineSession()); // seuil de 60 %, moyenne < 60%
}
java
@Test
void etantDonneEtudiantMathematiquesAvecUneMoyenneAuDessusDuSeuilDeReussiteLorsquOnVerifieEstAdmisALaProchaineSessionAlorsEstAdmis() {
    Etudiant etudiant = new EtudiantMathematiques("Bob", List.of(50, 52));

    assertTrue(etudiant.estAdmisALaProchaineSession()); // seuil de 50 %, moyenne de 51 %
}

estAdmisALaProchaineSession() (défini une seule fois, final, dans Etudiant) n'est jamais réécrit - seul getSeuilReussite() varie. Le tester dans les deux sous-classes vérifie à la fois le comportement commun et le seuil propre à chacune.

Implémentation concrète, classe privée ou mock ​

La meilleure façon de tester une classe abstraite est toujours de passer par une sous-classe concrète. Parfois ce n'est pas possible, on peut alors créer une classe privée dans notre classe de test ou créer un mock.

TechniqueCe qu'on testePourquoiPortée
Sous-classe concrète existanteUn comportement concret hérité, dans un contexte réelLa sous-classe existe déjà dans le domaineN'importe quelle méthode concrète de la super-classe
Classe concrète privée minimaleUn comportement concret de la super-classe, isolé de toute logique de sous-classeAucune sous-classe du domaine ne suffit à isoler ce comportement précisLe comportement concret de la super-classe seulement
Mock d'une classe abstraiteUne classe utilisatrice de la classe abstraiteIsoler le client de la classe abstraite, sans dépendre d'une implémentation concrèteLe code client - jamais le contrat abstrait lui-même

La classe concrète privée est un dernier recours, jamais un réflexe : si une sous-classe du domaine permet de tester le comportement voulu, on l'utilise.

Le mock, lui, ne sert jamais à tester la classe abstraite elle-même - seulement une classe qui la reçoit en paramètre ou en dépendance.

Généralisation de code ​

Une hiérarchie de plusieurs sous-classes (LivrePapierTest, LivreElectroniqueTest, etc.) répète certaines assertions communes à Livre. On assume cette duplication plutôt que d'introduire une classe de tests abstraite ou un héritage entre classes de tests : chaque classe de tests reste lisible seule, sans dépendance. Le coût de répéter quelques lignes de code reste inférieur à celui d'ajouter une indirection dans le code de test lui-même.

Généraliser la vérification d'un comportement hérité

Une classe utilitaire statique, nommée d'après la super-classe, peut regrouper les assertions qui vérifient ses comportements de base, sans imposer de lien d'héritage entre les classes de tests qui l'appellent.

java
public class LivreTestHelper {

    public static void verifierComportementsDeBase(Livre livre, String auteurAttendu, String titreAttendu) {
        assertEquals(auteurAttendu, livre.getAuteur(), "L'auteur ne correspond pas à celui du constructeur");
        assertEquals(titreAttendu, livre.getTitre(), "Le titre ne correspond pas à celui du constructeur");
        assertTrue(livre.toString().contains(titreAttendu), "toString() ne contient pas le titre");
        assertTrue(livre.toString().contains(auteurAttendu), "toString() ne contient pas l'auteur");
    }
}

LivreTest vérifie que la super-classe elle-même fournit ce comportement de base :

java
@Test
void etantDonneLivreApresInitialisationAlorsFournitUnComportementDeBase() {
    Livre livre = new Livre("Robert C. Martin", "Clean Code", "978-0-13-235088-4");

    LivreTestHelper.verifierComportementsDeBase(livre, "Robert C. Martin", "Clean Code");
}

LivrePapierTest vérifie que la sous-classe respecte le même comportement de base, hérité :

java
@Test
void etantDonneLivrePapierApresInitialisationAlorsRespecteLesComportementsDeBase() {
    LivrePapier livre = new LivrePapier("Robert C. Martin", "Clean Code", "978-0-13-235088-4", 464);

    LivreTestHelper.verifierComportementsDeBase(livre, "Robert C. Martin", "Clean Code");
}

LivreTestHelper ne teste rien par elle-même - elle centralise des assertions réutilisables.

limitations

Cette solution vient toutefois avec un coût de maintenance supplémentaire en plus d'assouplir la garantie que les sous-classes ne seront jamais modifiées involontairement.
