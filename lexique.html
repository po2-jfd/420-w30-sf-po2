Lexique ​

ACDEFGHIKLMNOPRSTUV

A

AAA
Patron AAA, Arrange-Act-Assert
Structure en trois étapes d'un test : Arrange (préparer l'état), Act (exécuter l'action testée), Assert (vérifier le résultat). Correspond à Étant donné/Lorsque/Alors dans le nommage. Voir aussi : Test automatisés
Abstraction
Un des quatre piliers de la POO : se concentrer sur ce qu'un objet fait plutôt que sur comment il le fait. Se réalise en Java par les classes abstraites et les interfaces. Voir aussi : Vue d'ensemble
Anti-patron
Anti-pattern
Solution récurrente à un problème courant qui semble raisonnable, mais qui nuit à la qualité du code (p. ex. l'obsession des primitives).

C

Classe abstraite
Classe qui ne peut pas être instanciée directement et sert de modèle pour d'autres classes. Elle peut contenir des méthodes abstraites (sans implémentation) que les sous-classes doivent définir. Voir aussi : Classes abstraites
Clause de garde
Guard clause, Early return
Condition placée en tête de méthode qui rejette immédiatement les cas invalides (retour ou exception), évitant l'imbrication de conditions et gardant le chemin normal au niveau zéro d'indentation. Voir aussi : Code propre
Code propre
Clean Code
Code qui est lisible, compréhensible et maintenable. Il suit des conventions de nommage, des principes de conception et évite la duplication et la complexité inutile.
Cohésion
Degré auquel les éléments d'un module ou d'une classe sont liés et travaillent ensemble pour accomplir une tâche spécifique. Une forte cohésion est souhaitable pour la clarté et la réutilisabilité du code. Voir aussi : SRP - Responsabilité unique
Composante
Objet qui fait partie d'un objet plus complexe, souvent utilisé pour construire des objets plus grands à partir de composants plus petits.
Composition
Mécanisme qui établit une relation A_UN entre un objet composé et ses composants, auxquels il délègue les comportements qu'il ne réalise pas lui-même. Voir aussi : Composition vs héritage
Copie défensive
Technique consistant à copier un objet mutable reçu (constructeur) ou retourné (getter) plutôt que de partager la référence originale, pour éviter les effets de bord. Voir aussi : Effets de bord
Couplage
Degré de dépendance entre différentes parties d'un système. Un couplage faible est souhaitable pour faciliter la maintenance et l'évolution du code.

D

Dépendance circulaire
Deux packages (ou classes) qui dépendent l'un de l'autre mutuellement. Brise la compilation et les tests en isolation; se règle en introduisant une interface ou un package partagé (DIP).
Dépôt distant
Remote Repository, Dépot git, Dépôt Github
Dépôt Git hébergé sur un serveur distant, permettant la collaboration et le partage de code entre plusieurs développeurs.
Développement piloté par les tests
Test-Driven Development, TDD
Méthodologie de développement logiciel où les tests sont écrits avant le code de production, guidant ainsi la conception et assurant la qualité du code. Voir aussi : TDD - cycle Rouge-Vert-Réusinage
Don't repeat yourself
DRY, Ne vous répétez pas
Principe de développement qui encourage la réduction de la duplication d'informations, favorisant la réutilisation et la maintenabilité en centralisant la connaissance.
Doublure de test
Test double
Terme générique pour un objet de remplacement utilisé dans un test afin de contrôler une dépendance. Cinq types, du moins au plus sophistiqué : Dummy, Stub, Fake, Espion, Mock. Voir aussi : Mocks (dummy, stub, fake, spy, mock)
DTO
Data Transfer Object
Objet immuable dont le seul rôle est de transporter des données entre les couches (souvent modèle ↔ vue), sans comportement. Créé et transformé par un convertisseur.
Dummy
Fantôme
Doublure de test vide qui ne fait rien; sert uniquement à satisfaire une signature (paramètre requis mais non utilisé dans le test). Voir aussi : Mocks (dummy, stub, fake, spy, mock)

E

Effacement de type
Type erasure
Les informations génériques n'existent qu'à la compilation; à l'exécution, List<String> et List<Integer> partagent la même classe List. Voir aussi : Génériques
Effet de bord
Side effect
Modification imprévue d'un état partagé, typiquement causée par le partage d'une référence (constructeur ou getter qui expose un objet mutable interne). Voir aussi : Effets de bord
Encapsulation
Pilier de la POO consistant à regrouper données et comportements dans une classe tout en contrôlant l'accès (private/public) pour valider, cacher l'implémentation et maintenir les invariants. Voir aussi : Encapsulation
Entité
Entity
Objet qui représente un concept ou un élément du domaine d'affaire, généralement identifiable par un identifiant unique et ayant une identité propre.
Énumération
Enum
Type dont les valeurs possibles sont toutes connues à la compilation; remplace avantageusement les constantes int/String pour garantir la sécurité de type. Voir aussi : Énumérations
Espion
Spy
Doublure de test qui enregistre les appels reçus (nombre, arguments) pour permettre de les vérifier après coup - utile quand le comportement testé est void et n'est pas observable autrement. Voir aussi : Mocks (dummy, stub, fake, spy, mock)
Exception
Mécanisme qui interrompt le flux normal d'exécution lors d'une situation anormale et remonte la pile d'appels jusqu'à un gestionnaire (catch). Hérite de Throwable.
Exception non vérifiée
Unchecked exception
Hérite de RuntimeException; le compilateur ne force ni sa déclaration (throws) ni sa gestion. Utilisée dans ce cours pour toutes les erreurs du domaine. Voir aussi : Exceptions non vérifiées (unchecked)
Exception personnalisée
Exception créée pour le domaine, héritant de RuntimeException, qui apporte sémantique (nom explicite) et contexte (champs). Placée dans le même package que la classe qui la lance. Voir aussi : Exceptions personnalisées
Exception vérifiée
Checked exception
Hérite directement de Exception; le compilateur oblige à la gérer (try/catch) ou à la déclarer (throws). Rencontrée uniquement dans les API Java standard (I/O, JDBC) - pas utilisée pour le domaine dans ce cours. Voir aussi : Exceptions vérifiées (checked)

F

Fabrique simple
Simple Factory
Classe dont l'unique rôle est de créer des objets, centralisant le switch/if sur le type à créer. Seule classe autorisée à contenir ce genre de switch (règle G23). Voir aussi : Fabrique simple (Simple Factory)
Façade
Facade
Patron de conception qui offre une interface simplifiée vers un ensemble de classes plus complexe, en cachant leurs détails à l'appelant.
Fake
Substitut
Doublure de test avec une logique minimale qui retourne des valeurs différentes selon les paramètres reçus. Voir aussi : Mocks (dummy, stub, fake, spy, mock)
FIFO
First In, First Out
Premier entré, premier sorti : ordre de retrait d'une file (Queue). Voir aussi : Types de collections
Fusion
Merge
Intégration des commits d'une branche dans une autre. Le merge classique conserve tous les commits; le squash and merge les regroupe en un seul. Voir aussi : Fusion (merge vs squash)

G

G23
Règle G23
Règle de Clean Code stipulant qu'il ne doit pas y avoir plus d'une instruction switch/if-else pour un type donné de sélection. La Fabrique Simple est la seule classe autorisée à contenir ce switch; ailleurs, on préfère le polymorphisme. Voir aussi : Polymorphisme
Générique
Generics
Mécanisme permettant d'écrire du code paramétré par un type (List<T>), assurant la sécurité de type à la compilation et éliminant les transtypages (cast) manuels. Voir aussi : Génériques

H

Héritage
Mécanisme qui établit une relation de sous-typage EST_UN entre une sous-classe et sa super-classe, dont la sous-classe acquiert les attributs et comportements, avec la possibilité de les redéfinir ou de les étendre. Voir aussi : Héritage

I

Immuabilité
Objet immuable, Immutable
Propriété d'un objet qui ne peut pas être modifié après sa création (classe final, attributs private final, pas de setters, copie défensive). Élimine les effets de bord liés aux références partagées. Voir aussi : Effets de bord
Injection de dépendances
Dependency Injection
Technique consistant à fournir à une classe ses collaborateurs de l'extérieur (par constructeur, par mutateur ou en paramètre de méthode) plutôt que de les créer elle-même. Voir aussi : Injection de dépendances
Intégration continue
CI, Continuous Integration
Pratique d'exécuter automatiquement compilation et tests à chaque push/PR (ex: GitHub Actions), pour détecter les problèmes tôt dans un environnement neutre.
Interface
Contrat qui définit un ensemble de méthodes qu'une classe doit implémenter, sans fournir d'implémentation concrète. Permet de définir des comportements communs pour différentes classes. Voir aussi : Interfaces
Invariant
Condition qui doit toujours être vraie pour un objet ou un système, garantissant la cohérence et la validité de son état. Voir aussi : Préconditions et validation
Inversion des dépendances
Dependency Inversion Principle, DIP
Principe SOLID qui stipule de dépendre des abstractions (interfaces) plutôt que des implémentations concrètes, autant pour les modules de haut niveau que de bas niveau. Voir aussi : DIP - Inversion des dépendances

K

Keep It Simple, Stupid
KISS
Principe de conception qui encourage la simplicité et la clarté dans le code, évitant les complexités inutiles et favorisant des solutions directes et compréhensibles.

L

LIFO
Last In, First Out
Dernier entré, premier sorti : ordre de retrait d'une pile (Stack, Deque). Voir aussi : Types de collections
Loi de Déméter
Principe qui limite les interactions d'un objet à ses « amis les plus proches » afin de réduire le couplage. Voir aussi : Expert de l'information (TDA, Déméter)

M

Mock
Simulacre, Objet simulé
Doublure de test la plus sophistiquée : peut faire échouer le test en validant les appels reçus. Un mock doit toujours implémenter une interface. Voir aussi : Mocks (dummy, stub, fake, spy, mock)
MVC
Modèle-Vue-Contrôleur, Model-View-Controller
Patron architectural en trois couches : le modèle (domaine, ignore tout du reste), la vue (affiche des DTOs, ignore le modèle), le contrôleur (orchestre les deux, connaît modèle ET vue).

N

NullObject
Objet qui implémente une interface mais ne fait rien, utilisé pour éviter les null et les if dans le code de l'application.

O

Objet paramètre
Parameter Object
Objet qui encapsule plusieurs paramètres d'une méthode ou d'une fonction, simplifiant ainsi la signature et améliorant la lisibilité du code. Voir aussi : Objets paramètres
Objet valeur
Value Object
Objet qui représente une valeur et est immuable, souvent utilisé pour encapsuler des données simples. Se compare par l'ensemble de ses valeurs Voir aussi : Value Objects
Observateur
Observer
Patron de conception qui définit une dépendance unidirectionnelle entre des objets, permettant à un objet (l'observateur) de surveiller les changements d'un autre objet (le sujet) et d'être notifié automatiquement en cas de modification.
Obsession des primitives
Primitive Obsession
Anti-patron consistant à représenter un concept du domaine avec un type primitif (String, int, double) plutôt qu'un objet dédié. Solutions : Value Object, objet paramètre, ou interface (stratégie). Voir aussi : Obsession des primitives
Odeur de code
Code smell
Signe indiquant un problème de conception sans être un bogue (méthode trop longue, duplication, valeurs magiques, trop de paramètres, chaîne de messages). Déclenche un réusinage. Voir aussi : Réusinage (refactoring)
Optional
Type Java (java.util.Optional) qui représente une valeur possiblement absente. La signature annonce l'absence possible et oblige l'appelant à la traiter explicitement. Voir aussi : Exceptions, les bonnes pratiques
Ordonne, ne demande pas
TDA, Tell-Don't-Ask
Principe qui invite à ordonner un objet plutôt que de lui demander son état pour décider à sa place. Voir aussi : Expert de l'information (TDA, Déméter)
Ouvert/fermé
Open/Closed Principle, OCP
Principe SOLID qui stipule qu'une entité logicielle (classe, module, fonction) doit être ouverte à l'extension mais fermée à la modification. Voir aussi : OCP - Ouvert / Fermé

P

Patrons de conception
Design Patterns
Solutions réutilisables à des problèmes courants de conception logicielle, fournissant des modèles éprouvés pour structurer et organiser le code.
Pile d'appels
Trace de pile, Stack Trace, Call Stack
Liste des appels de méthodes actifs au moment où une exception est lancée, affichée du point de lancement (en haut) jusqu'au point d'entrée (en bas) - se lit de bas en haut pour retracer le chemin d'exécution.
Point d'extension
Méthode abstraite (souvent `protected`) qu'une classe abstraite laisse à implémenter par ses sous-classes, appelée depuis une méthode d'orchestration `final` de la super-classe. Voir aussi : Classes abstraites
POJO
Plain Old Java Object
Objet Java simple, sans dépendances spécifiques à un framework, souvent utilisé pour représenter des données. Voir aussi : POJO vs Records
Polymorphisme
Capacité d'un objet à se substituer à d'autres objets d'un type compatible, permettant d'utiliser une interface commune pour différents types d'objets. Voir aussi : Polymorphisme
Postcondition
Condition qui doit être vraie après l'exécution d'une méthode ou d'une fonction, garantissant ce qu'elle promet à ses appelants. Voir aussi : Préconditions et validation
Précondition
Condition qui doit être vraie avant l'exécution d'une méthode ou d'une fonction pour garantir son bon fonctionnement. Voir aussi : Préconditions et validation
Principe de fermeture commune
Common Closure Principle, CCP
Principe de conception qui stipule que les classes qui changent pour les mêmes raisons devraient être regroupées dans le même module ou package. Voir aussi : CCP et CRP - cohésion des packages
Principe de réutilisation commune
Common Reuse Principle, CRP
Principe de conception qui stipule que les classes qui sont utilisées ensemble devraient être regroupées dans le même module ou package. Voir aussi : CCP et CRP - cohésion des packages
Pull Request
PR
Demande d'intégration d'une branche vers une autre sur GitHub, déclenchant un processus de revue de code par les coéquipiers avant la fusion. Voir aussi : Pull request et revue de code

R

Record
Type de classe Java (16+) conçu pour les données immuables; génère automatiquement constructeur, accesseurs (sans préfixe get), equals, hashCode et toString. Ne peut pas hériter.
Redéfinition
Override, Overriding
Mécanisme permettant à une sous-classe d'adapter (@Override) le comportement d'une méthode héritée, en la remplaçant ou en l'augmentant via super.methode(). Résolue dynamiquement à l'exécution - contrairement à la surcharge. Voir aussi : Redéfinition de méthodes (@Override)
Régression
Bogue introduit dans une partie du code qui fonctionnait auparavant, souvent causé par des modifications ou des ajouts de fonctionnalités.
Repository
Patron de conception qui fournit une interface pour accéder aux données d'une source de données, encapsulant la logique de persistance et permettant de séparer les préoccupations entre la couche de domaine et la couche d'accès aux données.
Responsabilité unique
Single Responsibility Principle, SRP
Principe SOLID qui stipule qu'une classe ne devrait avoir qu'une seule raison de changer. Voir aussi : SRP - Responsabilité unique
Réusinage
Refactoring
Processus de restructuration du code pour améliorer sa qualité sans en modifier le comportement externe. Voir aussi : Réusinage (refactoring)
Revue de code
Code review
Examen du code d'un pair avant intégration : lire les tests d'abord, vérifier les conventions et les principes SOLID, commenter précisément et de façon constructive. Voir aussi : Revue de code
Routeur
Composante qui achemine chaque requête émise par une vue vers le contrôleur approprié, de sorte que la vue n'a pas à connaître le contrôleur.

S

Screaming architecture
Architecture explicite
Principe de conception qui suggère que la structure et les noms des composants d'une application devraient refléter clairement son domaine et ses fonctionnalités, facilitant ainsi la compréhension du système. Voir aussi : Organisation des classes
Ségrégation des interfaces
Interface Segregation Principle, ISP
Principe SOLID qui stipule qu'une classe ne doit pas être forcée d'implémenter des interfaces qu'elle n'utilise pas, favorisant ainsi la création d'interfaces spécifiques plutôt que générales. Voir aussi : ISP - Ségrégation des interfaces
Séparation des commandes et des requêtes
CQS, Command-Query Separation
Principe qui stipule que les méthodes d'un objet doivent être soit des commandes (modifiant l'état), soit des requêtes (renvoyant des informations), mais pas les deux. Voir aussi : Séparation des commandes et des requêtes (CQS)
SOLID
Acronyme des cinq principes de conception objet : Responsabilité unique (S), Ouvert/fermé (O), Substitution de Liskov (L), Ségrégation des interfaces (I), Inversion des dépendances (D). Voir aussi : SOLID - vue d'ensemble
Sous-classe
Classe dérivée, Classe enfant
Classe qui hérite d'une autre classe (la super-classe) et peut redéfinir ou étendre son comportement. Voir aussi : Héritage
Stratégie
Strategy
Patron de conception qui permet de définir une famille d'algorithmes, de les encapsuler et de les rendre interchangeables, permettant ainsi de modifier le comportement d'un objet à l'exécution. Voir aussi : Stratégie (Strategy)
Stratégie de branche
Branching Strategy
Méthodologie de gestion des branches dans un système de contrôle de version, définissant comment les développeurs créent, fusionnent et publient les branches pour organiser le développement et la livraison du code. Voir aussi : Branches
Stub
Bouchon
Doublure de test qui retourne toujours une valeur fixe pour une méthode donnée, sans logique. Voir aussi : Mocks (dummy, stub, fake, spy, mock)
Substitution de Liskov
Liskov Substitution Principle, LSP
Principe SOLID qui stipule que les objets d'une classe dérivée doivent pouvoir être substitués à des objets de la classe de base sans altérer le comportement attendu du programme. Voir aussi : LSP - Substitution de Liskov
Super-classe
Classe de base, Classe parent
Classe dont hérite une autre classe (la sous-classe). Elle définit le type attendu par les clients et le contrat que chaque sous-classe s'engage à respecter. Voir aussi : Héritage
Surcharge
Overloading
Ajout d'une méthode de même nom mais de signature différente (paramètres). Résolue à la compilation selon le type déclaré des arguments - contrairement à la redéfinition, résolue à l'exécution. Voir aussi : Redéfinition de méthodes (@Override)

T

Test flaky
Test qui passe ou échoue de façon inconsistante sans changement du code, généralement causé par une dépendance non déterministe (horloge, ordre d'exécution, état partagé). Se corrige en isolant la dépendance via un stub. Voir aussi : Couverture et bonnes pratiques
Types de tests
Test unitaire, Test d'intégration, Test E2E
Trois niveaux selon la portée : unitaire (une classe, isolée, rapide), intégration (plusieurs composantes), bout-en-bout/E2E (tout le système, lent). Ce cours se limite aux tests unitaires.

U

UML
Unified Modeling Language
Langage de modélisation graphique pour représenter les systèmes logiciels, incluant des diagrammes de classes, de séquence, d'activités et d'états. Voir aussi : UML - Modélisation des classes et des objets

V

Valeur magique
Magic Value
Valeur codée en dur dans le code source, souvent utilisée pour représenter des constantes ou des paramètres spécifiques. L'utilisation de valeurs magiques est déconseillée, car elles rendent le code moins lisible et plus difficile à maintenir.
Valeur sentinelle
Sentinel Value
Valeur spéciale retournée pour signaler un cas particulier, comme -1 pour indiquer qu'un élément est absent (ex. List.indexOf). L'appelant doit connaître la convention et penser à la vérifier. Voir aussi : Exceptions, les bonnes pratiques
