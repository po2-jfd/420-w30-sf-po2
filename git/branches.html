Branches ​

Une branche est une ligne de développement indépendante : elle permet de modifier le code sans affecter les autres branches, le temps de développer une fonctionnalité ou de corriger un bogue. Cette isolation permet à plusieurs personnes de travailler en parallèle sur le même dépôt sans se marcher sur les pieds, et de garder le code en production à l'abri de changements incomplets.

Une équipe adopte généralement une stratégie de branches : une convention qui précise quelles branches sont permanentes et protégées, lesquelles sont éphémères, et comment le code circule entre elles. La stratégie présentée ici distingue main, develop et les branches de fonctionnalité.

Objectifs d'apprentissage ​

Après cette section, tu seras capable de...

  • Expliquer le rôle de main, develop et des branches de fonctionnalité
  • Créer et changer de branche avec Git
  • Travailler sur une branche de fonctionnalité et la pousser

Structure - trois types de branches ​

main ──────────────────────────────────► (production stable)
      \                     /
develop ─────────────────────────────►  (intégration)
           \        /
            feature  (fonctionnalité)
BrancheDuréeRôle
mainPermanenteCode en production - toujours stable
developPermanenteIntégration des fonctionnalités complétées
featureÉphémèreDéveloppement d'une fonctionnalité

Commandes Git pour les branches ​

bash
# Voir les branches locales
git branch

# Voir toutes les branches (locales + distantes)
git branch -a

# Créer et basculer sur une nouvelle branche
git checkout -b a1-ajouter-validation-salaire

# Basculer sur une branche existante
git checkout develop

# Pousser la branche vers le dépôt distant
git push origin a1-ajouter-validation-salaire

Flux de travail complet ​

1. Partir de develop à jour ​

Récupère tous les changements survenus sur le dépôt distant.

bash
git checkout develop
git pull origin develop

2. Créer une branche de fonctionnalité ​

La branche existe localement. La modification -b appliquée sur checkout permet de créer une nouvelle branche et de basculer vers celle-ci.

bash
git checkout -b a1-ajouter-validation-salaire

La convention de nommage : x#-ma-fonctionnalité en kebab-case, où x est le code du récit, # son numéro (ex. a1) et ma-fonctionnalité une description courte.

Structure de préfixes pour les branches

D'autres standards de nommage proposent une approche différente : un préfixe indiquant la nature de la branche, suivi du même identifiant de récit et de la description.

PréfixeUsageExemple
feature/Nouvelle fonctionnalitéfeature/a12-validation-salaire
bug/Correction d'un boguebug/a15-erreur-calcul-taxe
hotfix/Correction urgente en production, part de mainhotfix/a20-crash-connexion
release/Préparation d'une mise en productionrelease/1.4.0
chore/Tâche technique sans impact fonctionnelchore/a8-mise-a-jour-dependances

Ce standard à préfixes (feature/, bug/, etc.) n'est pas utilisé dans ce cours. Les branches créées suivent uniquement le format x#-ma-fonctionnalité, sans préfixe. Il est présenté ici pour référence, car il est répandu dans l'industrie sous le nom de Git Flow.

3. Développer (code + tests) ​

bash
# Travailler, committer régulièrement
git add src/main/java/Employe.java
git commit -m "feat: ajouter validation salaire dans constructeur"

Code de production et tests

Chaque commit doit inclure le code de production ET les tests pertinents. De cette façon, on peut revenir en arrière un commit à la fois sans devoir faire de nettoyage

4. Synchroniser le code distant ​

Lors du développement en équipe il est très probable que la branche develop ait changé depuis le début de notre développement. Il faut ramener les changements distants dans notre branche et traiter les conflits.

bash

git checkout develop # on bascule sur la branche avec laquelle on veut se synchroniser
git pull # on récupère les changements distants

git checkout a1-ajouter-validation-salaire # on retourne sur notre branche
git merge develop # on ramène les changements de dévelop sur notre branche

Si des conflits entre notre code et le code distant surviennent, c'est à ce moment qu'on les règle.

5. Pousser la branche ​

Rends la branche disponible sur le dépôt distant.

bash
git push origin a1-ajouter-validation-salaire

6. Créer une Pull Request ​

Sur GitHub : ouvrir une PR de a1-ajouter-validation-salaire vers develop.

Bonnes pratiques ​

Branches courtes

Une branche de fonctionnalité doit durer 1 à 3 jours maximum. Une branche qui vit longtemps diverge de develop et accumule des conflits potentiels.

  • Une fonctionnalité = une branche - pas de branches multi-fonctionnalités
  • Nommer clairement - a3-formulaire-employe plutôt que a3-fix
  • Partir toujours de develop à jour - évite les conflits inutiles
  • Garder les branches petites - une grande fonctionnalité peut nécessiter plusieurs petites branches
