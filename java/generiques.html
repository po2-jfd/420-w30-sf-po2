Génériques ​

Les génériques (generics) permettent d'écrire du code qui fonctionne avec différents types tout en conservant la sécurité des types à la compilation. Ils éliminent les transtypages (cast) explicites et détectent les erreurs de type dès la compilation.

Objectifs d'apprentissage ​

Après cette section, tu seras capable de...

  • Déclarer une classe ou méthode générique
  • Utiliser les génériques avec les collections
  • Expliquer l'effacement de type (type erasure)
  • Appliquer les bornes (extends, super) dans des contextes simples

Problème sans génériques ​

Avant Java 5, les collections stockaient des Object. Le transtypage était manuel et risqué :

java
// Sans génériques
List maListe = new ArrayList();
maListe.add("Alice");
maListe.add(42);          // compile - aucune protection!

String nom = (String) maListe.get(1); // ClassCastException à l'exécution!

Avec génériques ​

java
// Avec génériques - erreur détectée à la compilation
List<String> noms = new ArrayList<>();
noms.add("Alice");
noms.add(42);       // ERREUR DE COMPILATION - int incompatible avec String

String nom = noms.get(0); // pas de transtypage nécessaire

Collections génériques ​

La syntaxe <Type> spécifie le type des éléments :

java
List<Employe> employes = new ArrayList<>();
Map<String, Integer> scores = new HashMap<>();
Set<LocalDate> joursOuverts = new HashSet<>();

Opérateur diamant (diamond operator)

Depuis Java 7, le compilateur infère le type générique à droite de l'affectation - le <> vide suffit :

java
// Avant Java 7
List<Employe> employes = new ArrayList<Employe>();

// Depuis Java 7
List<Employe> employes = new ArrayList<>();

Classe générique personnalisée ​

java
public class Paire<A, B> {
    private final A premier;
    private final B second;

    public Paire(A premier, B second) {
        this.premier = premier;
        this.second = second;
    }

    public A getPremier() { return this.premier; }
    public B getSecond()  { return this.second; }
}
java
Paire<String, Integer> score = new Paire<>("Alice", 95);
System.out.println(score.getPremier()); // Alice
System.out.println(score.getSecond());  // 95

Méthode générique ​

java
public static <T> T premierElement(List<T> liste) {
    if (liste.isEmpty()) {
        throw new NoSuchElementException("La liste est vide.");
    }
    return liste.get(0);
}
java
List<String> noms = List.of("Alice", "Bob");
String premier = premierElement(noms); // Alice - pas de transtypage

Bornes sur les génériques ​

Le problème : génériques et héritage ​

Attention : List<Integer> n'est pas un sous-type de List<Number>, même si Integer extends Number.

java
List<Integer> entiers = new ArrayList<>();
List<Number> nombres = entiers;  // ERREUR DE COMPILATION

// Solution : joker (wildcard)
List<? extends Number> nombresEnLecture = entiers;  // OK (lecture seule)

Pourquoi cette interdiction?

Si Java acceptait l'affectation, entiers et nombres désigneraient la même liste. Par la référence nombres, on pourrait y ajouter n'importe quel Number, et donc corrompre une liste censée ne contenir que des entiers :

java
List<Integer> entiers = new ArrayList<>();
List<Number> nombres = entiers;   // supposons que ce soit permis

nombres.add(3.5);                 // légal : un Double est un Number
Integer premier = entiers.get(0); // erreur : c'est un Double, pas un Integer!

Une List<Number> promet deux choses : on peut y lire des Number, et on peut y ajouter n'importe quel Number. Une List<Integer> respecte la première promesse, mais pas la seconde. Elle ne peut donc pas remplacer une List<Number>.

Les jokers servent justement à indiquer quelle promesse on utilise : extends pour lire, super pour ajouter.

Les bornes règlent ce problème : une méthode accepte une famille de types plutôt qu'un seul.

extends - borne supérieure ​

Les éléments sont de type Number ou d'une de ses sous-classes : tout nombre.

java
// Accepte List<Integer>, List<Double>, List<Number>...
public static double somme(List<? extends Number> nombres) {
    double total = 0;
    for (Number n : nombres) {
        total += n.doubleValue();
    }
    return total;
}

super - borne inférieure ​

Les éléments sont de type Integer ou d'une de ses super-classes.

Problème : avec ajouterNotes(List<Integer>), on ne peut pas ajouter des notes dans une List<Number>, même si cette liste accepte des entiers :

java
List<Number> mesures = new ArrayList<>();
mesures.add(3.5);

ajouterNotes(mesures);  // ✗ avec List<Integer>
                        // ✓ avec List<? super Integer>
java
// Accepte List<Integer>, List<Number>, List<Object>...
public static void ajouterNotes(List<? super Integer> destination) {
    destination.add(85);
    destination.add(92);
}

Règle pratique

extends pour lire, super pour ajouter.

Pourquoi? Une List<? extends Number> peut être une List<Double> : y ajouter un Integer serait incorrect. Une List<? super Integer> peut être une List<Object> : les éléments lus ne sont garantis que comme Object.

Effacement de type (type erasure) ​

Les informations génériques n'existent qu'à la compilation. À l'exécution, toutes les instances de List<String>, List<Integer>, etc., sont simplement des List. C'est l'effacement de type.

java
List<String> noms = new ArrayList<>();
List<Integer> ids  = new ArrayList<>();

System.out.println(noms.getClass() == ids.getClass()); // true - même classe!

Ce mécanisme garantit la compatibilité avec le code Java pré-génériques.
