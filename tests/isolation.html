Isolation des dépendances ​

L'isolation est la capacité à tester une classe sans être affecté par le comportement de ses dépendances. Elle est rendue possible par l'injection de dépendances et les interfaces : une dépendance fournie de l'extérieur est une dépendance qu'un test peut remplacer.

Objectifs d'apprentissage ​

Après cette section, tu seras capable de...

  • Identifier les dépendances d'une classe à isoler
  • Concevoir une classe pour qu'elle soit testable en isolation
  • Choisir le point d'injection qui rend une dépendance remplaçable dans un test
  • Différencier les cas où une doublure est nécessaire

Problème - dépendance impossible à contrôler ​

java
// ✗ La dépendance est créée directement dans le code
public class RapportService {
    public String genererRapport() {
        EmployeDbRepository repository = new EmployeDbRepository();  // impossible à remplacer!
        List<Employe> employes = repository.getEmployes();
        // ...
    }
}

Pour tester RapportService, on doit avoir un vrai repository d'employé et potentiellement une vraie base de données. Ce n'est plus un test unitaire.

Solution - injecter la dépendance ​

java
// ✓ La dépendance est injectée (et donc remplaçable)
public class RapportService {
    private final EmployeRepository repository;  // interface

    public RapportService(EmployeRepository repository) {
        this.repository = repository;
    }

    public String genererRapport() {
        List<Employe> employes = this.repository.findAll();
        // ...
    }
}

Dans les tests, on injecte un mock :

java
@Test
void etantDonneListeEmployesLorsquOnGenereRapportAlorsRapportContientTousLesEmployes() {
    // ARRANGE
    List<Employe> employes = List.of(
        new Employe("Alice", 50_000),
        new Employe("Bob", 45_000)
    );
    EmployeRepository employeRepositoryMock = new EmployeRepositoryMock(employes);
    RapportService service = new RapportService(employeRepositoryMock);

    // ACT
    String rapport = service.genererRapport();

    // ASSERT
    assertTrue(rapport.contains("Alice"));
    assertTrue(rapport.contains("Bob"));
}

Quand isoler une dépendance? ​

SituationIsoler?Raison
La dépendance est non déterministe (heure, random, réseau)OuiLe test doit être reproductible
La dépendance est lente (base de données, service Web)OuiLe test doit être rapide
La dépendance n'est pas encore implémentéeOuiLe stub simule le service manquant
La configuration du test est plus compliquée que le test lui-mêmeOuiLe test doit être simple
La dépendance est un objet de valeur simple (double, int)NonPas besoin de doublure
La dépendance est un objet immuable de Java (String, Integer, LocalDate)NonComportement prévisible et stable

Types de dépendances externes fréquentes ​

java
// Base de données
public interface EmployeRepository {
    List<Employe> findAll();
    Optional<Employe> findById(int id);
    void save(Employe employe);
}

// Service d'envoi de courriel
public interface NotificationService {
    void envoyerCourriel(String destinataire, String sujet, String corps);
}

// Capteur ou source de données externe
public interface SourceTemperature {
    double lireTemperature();
}

Chacune peut être remplacée par un mock dans les tests.

Choisir le point d'injection ​

Les trois points d'injection se distinguent par la durée de vie de la dépendance. Le test se branche au même endroit que le code de production.

Par constructeur - la dépendance est obligatoire et vaut pour toute la durée de vie de l'objet. C'est le cas le plus fréquent, et celui qui garantit qu'aucune instance ne peut exister sans sa dépendance :

java
public class RapportService {
    private final EmployeRepository repository;

    public RapportService(EmployeRepository repository) {
        this.repository = repository;
    }
}
java
RapportService service = new RapportService(new EmployeRepositoryMock(employes));

Par mutateur - la dépendance s'ajoute ou change après la création de l'objet. Utile quand un test veut remplacer une seule collaboration sur un objet déjà construit :

java
public class RapportService {
    private FormatRapport format = new FormatTexte();

    public void utiliserFormat(FormatRapport format) {
        this.format = format;
    }
}
java
RapportService service = new RapportService(repositoryMock);
service.utiliserFormat(new FormatCsv());

Par paramètre de méthode - la dépendance ne sert qu'à un appel et n'est pas conservée. C'est le point d'injection qui règle le plus simplement les dépendances non déterministes :

java
public interface Horloge {
    LocalDate aujourdhui();
}

public class RapportService {
    public String genererRapportMensuel(Horloge horloge) {
        LocalDate date = horloge.aujourdhui();
        // ...
    }
}
java
@Test
void etantDonneUneDateFixeLorsquOnGenereLeRapportMensuelAlorsLEnteteAfficheCeMois() {
    // ARRANGE
    Horloge horlogeFixe = () -> LocalDate.of(2026, 3, 15);
    RapportService service = new RapportService(repositoryMock);

    // ACT
    String rapport = service.genererRapportMensuel(horlogeFixe);

    // ASSERT
    assertTrue(rapport.contains("mars 2026"));
}

Sans cette injection, genererRapportMensuel() appellerait LocalDate.now() et le test échouerait au changement de mois - le cas typique du test intermittent.

Injection par constructeur - avantages

  • L'objet est toujours valide après la construction
  • Les dépendances sont explicites (visibles dans la signature)
  • Compatible avec final pour les attributs immuables

Une dépendance créée avec new n'est pas testable

Chaque new sur une dépendance volatile (base de données, service Web, horloge, générateur aléatoire) à l'intérieur d'une classe est un point que le test ne peut pas atteindre. C'est le même diagnostic que le DIP : la classe nomme une implémentation concrète au lieu de dépendre d'une abstraction qu'on lui fournit.
