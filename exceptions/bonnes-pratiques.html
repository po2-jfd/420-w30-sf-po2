Exceptions, les bonnes pratiques ​

Les exceptions sont un outil puissant, mais mal utilisées elles compliquent la lecture et masquent les vrais problèmes. Ces bonnes pratiques s'appliquent à tous les projets Java.

Objectifs d'apprentissage ​

Après cette section, tu seras capable de...

  • Attraper le type d'exception le plus spécifique possible
  • Écrire des messages d'exception utiles
  • Limiter le contenu d'un bloc try au strict minimum
  • Reconnaître les anti-patrons courants (catch silencieux, catch générique, exception utilisée pour le flot normal)
  • Préserver la cause originale lorsqu'on relance une exception
  • Choisir entre une valeur sentinelle, un Optional ou une exception selon le sens d'affaire d'une valeur absente

1. Attraper le type le plus spécifique ​

java
// ✗ Trop général - attrape NullPointerException, ArithmeticException, tout
try {
    traiter();
} catch (Exception e) {
    System.err.println("Erreur");
}

// ✓ Spécifique - on sait exactement ce qu'on gère
try {
    String contenu = lireFichier(chemin);
} catch (FileNotFoundException e) {
    System.err.println("Fichier introuvable : " + chemin);
} catch (IOException e) {
    System.err.println("Erreur de lecture : " + e.getMessage());
}

2. Ne jamais avaler une exception silencieusement ​

java
// ✗ Catch silencieux - le problème disparaît sans laisser de trace
try {
    charger();
} catch (IOException e) {
    // Rien ici - bogue invisible, très difficile à déboguer
}

// ✓ Option 1 : ne rien faire, on laisse l'exception remonter
public void initialiser() throws IOException {
    charger(); // l'exception remonte à l'appelant
}

// ✓ Option 2 : journaliser, si on peut poursuivre l'exécution
try {
    charger();
} catch (IOException e) {
    System.err.println("Impossible de charger : " + e.getMessage());
}

// ✓ Option 3 : relancer, si l'appelant doit réagir
try {
    charger();
} catch (IOException e) {
    throw new ServiceException("Échec du chargement", e);
}

Journaliser ou relancer, pas les deux

Journaliser puis relancer la même exception produit plusieurs entrées dans le journal pour un seul problème : chaque niveau qui attrape l'exception la journalise à nouveau.

3. Inclure les valeurs problématiques dans le message ​

java
// ✗ Message vague
throw new IllegalArgumentException("Valeur invalide");

// ✓ Message avec contexte - facilite le débogage
throw new IllegalArgumentException(
    "Le salaire doit être >= 0, reçu : " + salaire
);

throw new IllegalArgumentException(
    "Le code article '" + code + "' n'existe pas dans le catalogue"
);

4. Préserver la cause originale (exception chaînée) ​

Quand on transforme une exception en une autre, on préserve la cause originale pour le débogage :

java
// ✓ Exception chaînée - la cause originale est préservée dans la pile d'appels (stack trace)
public Configuration charger(String chemin) {
    try {
        String contenu = Files.readString(Path.of(chemin));
        return Configuration.analyser(contenu);
    } catch (IOException e) {
        throw new ConfigurationException("Impossible de lire la configuration : " + chemin, e);
        //                                                                                  ↑
        //                                                            cause originale passée
    }
}

5. Ne pas utiliser les exceptions pour le flot normal ​

Les exceptions sont pour les situations anormales, pas pour le flot de contrôle ordinaire :

java
// ✗ Exception utilisée comme return prématuré
public int chercher(List<Integer> liste, int valeur) {
    try {
        for (int i = 0; ; i++) {
            if (liste.get(i) == valeur) {
                throw new RuntimeException(String.valueOf(i));
            }
        }
    } catch (RuntimeException e) {
        return Integer.parseInt(e.getMessage());
    }
}

Signaler une valeur absente : trois options ​

Le return règle le cas où la valeur est trouvée. Reste à décider quoi faire lorsqu'elle est absente. Il n'y a pas de réponse technique unique : le bon choix dépend de ce que l'absence signifie pour le domaine d'affaire.

Pour illustrer, prenons une file d'attente de dossiers dans une clinique. La même recherche, trouver la position d'un dossier dans la file, peut avoir trois sens d'affaire différents.

Option 1 : retourner -1 (valeur sentinelle) ​

java
// Retourne la position du dossier, ou -1 s'il n'est pas dans la file
public int positionDe(int numeroDossier) {
    for (int i = 0; i < this.numerosDossiers.size(); i++) {
        if (this.numerosDossiers.get(i) == numeroDossier) {
            return i;
        }
    }
    return -1;
}

// Appelant : l'écran d'accueil affiche la position des dossiers
int position = file.positionDe(numeroDossier);
if (position >= 0) {
    ecran.afficher("Position dans la file : " + (position + 1));
}

Raison d'affaire : l'absence est fréquente et sans conséquence. L'écran d'accueil interroge la file en continu ; un dossier absent n'est tout simplement pas affiché.

C'est la convention de la bibliothèque Java (List.indexOf, String.indexOf), simple et sans coût supplémentaire.

Risque : rien n'oblige l'appelant à vérifier le -1. S'il l'oublie, numerosDossiers.get(-1) lancera une exception plus loin, loin de la cause réelle.

Option 2 : retourner un Optional<Integer> ​

java
// La signature annonce que la position peut être absente
public Optional<Integer> positionDe(int numeroDossier) {
    for (int i = 0; i < this.numerosDossiers.size(); i++) {
        if (this.numerosDossiers.get(i) == numeroDossier) {
            return Optional.of(i);
        }
    }
    return Optional.empty();
}

// Appelant : la réceptionniste répond à un patient qui téléphone
Optional<Integer> position = file.positionDe(numeroDossier);
if (position.isPresent()) {
    repondre("Vous êtes en position " + (position.get() + 1));
} else {
    repondre("Votre dossier n'est pas dans la file, voulez-vous l'y ajouter?");
}

Raison d'affaire : l'absence est un résultat normal qui demande une décision. Un patient qui n'est pas dans la file est un cas prévu du processus : on lui propose de l'ajouter.

La signature documente cette possibilité et oblige l'appelant à traiter les deux cas. C'est l'option à privilégier lorsque la méthode est utilisée par d'autres classes ou d'autres équipes.

Option 3 : lancer une exception ​

java
// Le dossier doit être dans la file : son absence est une anomalie
public int positionDe(int numeroDossier) {
    for (int i = 0; i < this.numerosDossiers.size(); i++) {
        if (this.numerosDossiers.get(i) == numeroDossier) {
            return i;
        }
    }
    throw new DossierIntrouvableException("Le dossier " + numeroDossier + " est absent de la file");
}

// Appelant : le médecin appelle le dossier qu'il vient de sélectionner dans la file
int position = file.positionDe(numeroDossierSelectionne);
file.retirer(position);

Raison d'affaire : l'absence est anormale. Le dossier vient d'être sélectionné dans la file : selon les règles du domaine, il doit s'y trouver. S'il est absent, c'est une incohérence (bogue, dossier déjà traité par un autre poste, données corrompues).

L'appelant n'a pas à prévoir ce cas dans son flot normal : l'exception interrompt le traitement et remonte jusqu'à un niveau capable de la gérer.

Risque : si l'absence devient un cas courant, l'appelant se retrouve à écrire un try-catch pour la gérer. On retombe alors dans l'anti-patron de cette section : une exception utilisée pour le flot normal.

Résumé des options ​

OptionL'absence est...L'appelant...Risque principal
-1Fréquente et sans conséquenceDoit connaître la conventionOubli de vérification, erreur plus loin
OptionalNormale, mais demande une décisionEst obligé de traiter les deux casSurcharge si l'absence n'arrive jamais
ExceptionAnormale, contraire aux règles d'affaireN'a rien à prévoir dans son flot normalTry-catch dans le flot normal si mal choisie

La question à se poser

« Si la valeur est absente, est-ce un cas prévu par le processus d'affaire, ou le signe que quelque chose ne va pas? » Un cas prévu se traite avec une valeur de retour (-1 ou Optional) ; une anomalie se signale avec une exception.

6. Nettoyer les ressources ​

java
// ✓ try-with-resources - fermeture automatique garantie
try (BufferedWriter ecrivain = new BufferedWriter(new FileWriter("sortie.txt"))) {
    ecrivain.write("Données");
} catch (IOException e) {
    System.err.println("Erreur d'écriture : " + e.getMessage());
}
// ecrivain.close() est appelé automatiquement, même en cas d'exception : pas besoin de finally

7. Minimiser le contenu du bloc try ​

Le bloc try doit contenir idéalement une seule instruction - celle qui peut lancer l'exception. Plus le bloc est grand, plus il est difficile d'identifier quelle ligne est responsable d'un échec, et plus le risque d'attraper des exceptions inattendues augmente.

java
// ✗ Bloc try trop large - quelle ligne lance IOException?
try {
    String chemin = this.construireChemin(id);
    String contenu = Files.readString(Path.of(chemin));
    Configuration config = Configuration.analyser(contenu);
    this.appliquer(config);
} catch (IOException e) {
    throw new ConfigurationException("Échec de la lecture", e);
}

// ✓ Bloc try minimal - seule la lecture peut lancer IOException
String chemin = this.construireChemin(id);
String contenu;
try {
    contenu = Files.readString(Path.of(chemin));
} catch (IOException e) {
    throw new ConfigurationException("Impossible de lire : " + chemin, e);
}
Configuration config = Configuration.analyser(contenu);
this.appliquer(config);

Un try, une responsabilité

Si un bloc try contient plusieurs appels susceptibles de lancer des exceptions différentes, c'est le signe qu'il faut le décomposer, ou extraire les appels dans une méthode privée pour garder un seul try.

8. Ne pas relancer sans valeur ajoutée ​

java
// ✗ Relancer sans valeur ajoutée - aucun contexte pour l'appelant
try {
    traiter(idCommande);
} catch (SQLException e) {
    throw new RuntimeException(e);  // pourquoi? quelle commande?
}

// ✓ Relancer avec le contexte du domaine
try {
    traiter(idCommande);
} catch (SQLException e) {
    throw new TraitementCommandeImpossibleException("La commande " + idCommande + " ne peut pas être traitée", e);
}
