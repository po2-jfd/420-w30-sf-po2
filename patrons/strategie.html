Stratégie (Strategy) ​

Le patron Stratégie permet de définir une famille d'algorithmes, de les encapsuler dans des classes séparées, et de les rendre interchangeables à l'exécution. C'est l'application directe du principe OCP : la classe qui utilise la stratégie n'a pas besoin d'être modifiée pour supporter un nouvel algorithme.

Objectifs d'apprentissage ​

Après cette section, tu seras capable de...

  • Implémenter le patron Stratégie avec une interface et des classes concrètes
  • Injecter une stratégie par constructeur, par mutateur ou par paramètre
  • Identifier quand le patron Stratégie est approprié
  • Expliquer comment la Stratégie applique OCP, DIP et la règle G23

Problème - code conditionnel qui grandit ​

Une facture applique un rabais selon une valeur discriminante (enum). Chaque nouveau type de rabais force une modification de Facture :

java
public enum Rabais {
    AUCUN,
    ETUDIANT,
    BREUVAGE_GRATUIT,
    VENDREDI_FOU;
}
java
// ✗ Facture enfreint l'OCP - elle est modifiée pour chaque nouveau type de rabais
public class Facture {
    public static final double RABAIS_ETUDIANT = .1;
    public static final double RABAIS_VENDREDI_FOU = .3;
    public static final int MONTANT_BREUVAGE = 3;

    private Rabais rabais = Rabais.AUCUN;

    public double total(Commande commande) {
        return switch (this.rabais) {
            case AUCUN -> commande.calculerSousTotal();
            case ETUDIANT -> commande.calculerSousTotal() * (1 - RABAIS_ETUDIANT);
            case BREUVAGE_GRATUIT -> max(0, commande.calculerSousTotal() - MONTANT_BREUVAGE);
            case VENDREDI_FOU -> commande.calculerSousTotal() * (1 - RABAIS_VENDREDI_FOU);
        };
    }
}

Ce switch sur le type de rabais enfreint aussi la règle G23 : la sélection d'un comportement selon un type devrait passer par le polymorphisme plutôt que par une instruction conditionnelle qui grossit à chaque ajout.

UML ​

Exemple de stratégie ​

1. Définir l'interface de la stratégie ​

java
public interface CalculateurRabais {
    double calculerMontant(Commande commande);
}

Pourquoi passer la Commande plutôt que le sous-total?

Un double (le sous-total) ne suffit pas à toutes les stratégies : RabaisBreuvage a besoin du prix du breuvage, pas du sous-total. Passer la Commande complète donne à chaque stratégie accès à toute l'information dont elle pourrait avoir besoin, sans devoir changer la signature de l'interface à chaque nouveau cas.

2. Créer les implémentations concrètes ​

java
public class AucunRabais implements CalculateurRabais {
    @Override
    public double calculerMontant(Commande commande) {
        return 0;
    }
}
java
public class RabaisEtudiant implements CalculateurRabais {
    public static final double RABAIS_ETUDIANT = .1;

    @Override
    public double calculerMontant(Commande commande) {
        return commande.calculerSousTotal() * RABAIS_ETUDIANT;
    }
}
java
public class RabaisEmploye implements CalculateurRabais {
    public static final double RABAIS_EMPLOYE = .2;

    @Override
    public double calculerMontant(Commande commande) {
        return commande.calculerSousTotal() * RABAIS_EMPLOYE;
    }
}
java
public class RabaisVendrediFou implements CalculateurRabais {
    public static final double RABAIS_VENDREDI_FOU = .3;

    @Override
    public double calculerMontant(Commande commande) {
        return commande.calculerSousTotal() * RABAIS_VENDREDI_FOU;
    }
}
java
// Le calcul du rabais peut dépendre d'autre chose que le sous-total
public class RabaisBreuvage implements CalculateurRabais {
    @Override
    public double calculerMontant(Commande commande) {
        return commande.getPrixBreuvage();
    }
}

Généraliser RabaisEtudiant, RabaisEmploye et RabaisVendrediFou ​

RabaisEtudiant, RabaisEmploye et RabaisVendrediFou ont exactement le même corps de méthode - seule la constante change. RabaisPourcentage généralise les trois : au lieu d'une classe par pourcentage, une seule classe reçoit le pourcentage en paramètre.

java
public class RabaisPourcentage implements CalculateurRabais {
    private final double pourcentageRabais;

    public RabaisPourcentage(double pourcentageRabais) {
        this.pourcentageRabais = pourcentageRabais;
    }

    @Override
    public double calculerMontant(Commande commande) {
        return commande.calculerSousTotal() * this.pourcentageRabais;
    }
}
java
// RabaisEtudiant, RabaisEmploye et RabaisVendrediFou n'ont plus besoin d'exister
CalculateurRabais rabaisEtudiant = new RabaisPourcentage(0.1);
CalculateurRabais rabaisEmploye = new RabaisPourcentage(0.2);
CalculateurRabais rabaisVendrediFou = new RabaisPourcentage(0.3);

Quand ne pas multiplier les stratégies

Les trois classes n'implémentaient pas trois algorithmes, mais un seul algorithme avec trois données. La Stratégie sert à faire varier un comportement ; ici, ce qui variait était un paramètre. Une classe par variante n'est justifiée que si le calcul lui-même diffère - sinon, une seule classe paramétrée suffit.

RabaisBreuvage survit à cette généralisation précisément parce qu'il calcule autrement (le prix du breuvage, pas un pourcentage du sous-total) : c'est bien un second algorithme, pas une donnée différente pour le même algorithme.

3. Injecter la stratégie dans la classe cliente ​

java
public class Facture {
    private static final CalculateurRabais RABAIS_DEFAUT = new AucunRabais();

    private CalculateurRabais rabais = RABAIS_DEFAUT;  // dépendance à l'interface

    public void assignerRabais(CalculateurRabais rabais) {
        this.rabais = Objects.requireNonNull(rabais);
    }

    public void retirerRabais() {
        this.rabais = RABAIS_DEFAUT;
    }

    public double total(Commande commande) {
        return max(0, commande.calculerSousTotal() - this.rabais.calculerMontant(commande));
    }
}

Ici, la stratégie est assignée par mutateur plutôt que par constructeur : une facture existe d'abord sans rabais particulier (AucunRabais par défaut), puis un rabais peut lui être assigné - et retiré - à n'importe quel moment de son cycle de vie.

Objects.requireNonNull plutôt qu'un if manuel

java
// ✓ Concis - une ligne, exception générique standard
this.rabais = Objects.requireNonNull(rabais);

// Équivalent manuel - plus verbeux, même exception générique
if (rabais == null) {
    throw new NullPointerException("rabais");
}
this.rabais = rabais;

Objects.requireNonNull est l'idiome standard : concis, et lance une NullPointerException - la même exception générique qu'un if manuel lancerait naturellement, avec en prime la valeur retournée pour l'assignation directe.

Le if manuel redevient nécessaire quand une exception personnalisée est requise (une exception du domaine plutôt qu'une exception générique de la bibliothèque standard) :

java
if (rabais == null) {
    throw new RabaisInvalideException("Le rabais ne peut pas être nul");
}
this.rabais = rabais;

4. Utilisation ​

java
Facture facture = new Facture();
facture.total(commande); // aucun rabais

facture.assignerRabais(new RabaisPourcentage(0.1));
facture.total(commande); // 10 % de rabais

// Autre type de rabais - aucune modification de Facture
facture.assignerRabais(new RabaisBreuvage());
facture.total(commande); // prix du breuvage retranché

facture.retirerRabais();
facture.total(commande); // aucun rabais, de nouveau

Injection : constructeur ou couplage direct ​

Une stratégie qui n'est jamais changée pendant la durée de vie de l'objet peut plutôt être injectée par constructeur. Sans injection, la classe cliente est couplée à une implémentation concrète :

java
// ✗ Facture est couplée à RabaisBreuvage - impossible d'utiliser un autre rabais
public class Facture {
    private final CalculateurRabais rabais = new RabaisBreuvage();

    public double total(Commande commande) {
        return max(0, commande.calculerSousTotal() - this.rabais.calculerMontant(commande));
    }
}
java
// ✓ Facture dépend de l'interface, la stratégie concrète est injectée
public class Facture {
    private final CalculateurRabais rabais;

    public Facture(CalculateurRabais rabais) {
        this.rabais = Objects.requireNonNull(rabais);
    }

    public double total(Commande commande) {
        return max(0, commande.calculerSousTotal() - this.rabais.calculerMontant(commande));
    }
}

Trois points d'injection ​

FormeSignatureQuand
ConstructeurFacture(CalculateurRabais rabais)dépendance obligatoire, fixe pour la durée de vie
MutateurassignerRabais(CalculateurRabais rabais)stratégie changeable à l'exécution
Paramètretotal(Commande commande, CalculateurRabais rabais)stratégie variable à chaque appel

Stratégie ou simple polymorphisme? ​

Toute stratégie est une application du polymorphisme, mais tout polymorphisme n'est pas une stratégie. Le critère qui distingue les deux est le contexte : il faut qu'une classe détienne l'abstraction (CalculateurRabais) et lui délègue le traitement. Sans contexte qui détient et délègue, il n'y a pas de patron Stratégie - seulement du polymorphisme ordinaire.

Risque de sur-ingénierie - deux pièges qui passent le test d'entrée

Ces deux cas respectent bien la structure Contexte/Stratégie/Stratégie concrète, mais sans variation réelle à masquer : appliquer le patron ici, c'est de la sur-ingénierie.

  • Une seule implémentation, aucune autre prévue. Interface, classe et injection payées pour zéro variation.
  • Une donnée déguisée en algorithme. Plusieurs classes qui ne diffèrent que par une valeur, comme RabaisEtudiant/RabaisEmploye/RabaisVendrediFou avant leur généralisation : ce qui varie est un paramètre, pas un comportement - une seule classe paramétrée suffit.

Tester le patron Stratégie ​

Une doublure de test de type stub permet de simuler une commande et de simplifier les tests.

java
// Stub - Commande a deux méthodes
class CommandeStub implements Commande {
    @Override
    public double calculerSousTotal() {
        return 100.0;
    }

    @Override
    public double getPrixBreuvage() {
        return 0.0;
    }
}

class RabaisPourcentageTest {

    @Test
    void etantDonneUnRabaisEnPourcentageLorsquOnCalculeLeMontantAlorsObtientLeMontantAttendu() {
        CalculateurRabais rabais = new RabaisPourcentage(0.1);
        Commande commande = new CommandeStub();

        double montant = rabais.calculerMontant(commande);

        assertEquals(10.0, montant, 0.001);
    }
}

class FactureTest {

    @Test
    void etantDonneUnRabaisAssigneLorsquOnCalculeLeTotalAlorsAppliqueLeRabaisAttendu() {
        // ARRANGE - stratégie stub contrôlée
        CalculateurRabais rabaisStub = commande -> 15.0; // interface fonctionnelle : une lambda suffit
        Commande commande = new CommandeStub();
        Facture facture = new Facture();
        facture.assignerRabais(rabaisStub);

        // ACT
        double total = facture.total(commande);

        // ASSERT
        assertEquals(85.0, total, 0.001);
    }
}

Patrons de conception liés ​

La Stratégie est en quelque sorte le « patron des patrons » : plusieurs autres patrons de comportement et de structure en sont des versions évoluées, avec des rôles ou des contraintes supplémentaires par rapport au trio Contexte/Stratégie/Stratégie concrète. Parmi ceux-ci : État (State), Observateur (Observer), Chaîne de responsabilités (Chain of Responsibility), Composite, Commande (Command), Itérateur (Iterator), Médiateur (Mediator) et Repository.
